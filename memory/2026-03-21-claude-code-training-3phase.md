## 📚 模块 1.1: 底层技术解析 (2h)

### 1. Pi 引擎机制

**核心概念**:
- **Pi = Planning + Implementation**
- Claude Code 会先规划，再执行
- 规划过程可干预

**关键技术**:
```
┌─────────────┐
│ 用户指令    │
└──────┬──────┘
       ▼
┌─────────────┐     ┌─────────────┐
│ Pi 引擎     │────▶│ 规划阶段    │
│ (规划+执行) │     │ - 理解意图  │
└──────┬──────┘     │ - 拆解任务  │
       │            │ - 生成计划  │
       │            └─────────────┘
       ▼
┌─────────────┐     ┌─────────────┐
│ 执行阶段    │────▶│ 验证阶段    │
│ - 调用工具  │     │ - 测试      │
│ - 修改文件  │     │ - 审查      │
│ - 运行命令  │     │ - 确认      │
└─────────────┘     └─────────────┘
```

**关键洞察**:
> Claude 不是"边想边说"，而是"先规划，再执行"。你可以在规划阶段干预。

---

### 2. Prompt Caching (提示词缓存)

**问题**: 每次对话都要重新发送大段上下文，浪费 token 和时间

**解决方案**: Prompt Caching

```
┌──────────────────────────────────────────┐
│ System Prompt (缓存)                      │
│ - Claude Code 核心指令                    │
│ - 工具定义                                │
│ - 约 10K tokens                           │
├──────────────────────────────────────────┤
│ CLAUDE.md (缓存)                          │
│ - 项目规范                                │
│ - 团队约定                                │
│ - 约 5K tokens                            │
├──────────────────────────────────────────┤
│ Skill Context (缓存)                      │
│ - 加载的 Skill                            │
│ - 参考文档                                │
│ - 约 10K tokens                           │
├──────────────────────────────────────────┤
│ 对话历史 (不缓存)                         │
│ - 用户问题                                │
│ - Claude 回复                             │
│ - 动态变化                                │
└──────────────────────────────────────────┘

缓存命中率 90% → 成本降低 90%
```

**关键洞察**:
> 把稳定的内容放在缓存区（CLAUDE.md、Skill），把动态内容放在对话区。

### 3. 上下文管理策略

**三层上下文模型**:

| 层级 | 内容 | 生命周期 | 示例 |
|------|------|---------|------|
| **System** | Claude Code 核心指令 | 永久 | 工具定义、安全规则 |
| **Project** | CLAUDE.md + Skills | 项目级 | 编码规范、API 文档 |
| **Session** | 对话历史 | 会话级 | "帮我写登录功能" |

**管理原则**:
```
1. System 层 → 不动（Anthropic 控制）
2. Project 层 → 精心设计（CLAUDE.md + Skills）
3. Session 层 → 保持简洁（避免历史膨胀）
```

### 2. 工作流设计

**标准工作流**:

```
用户输入 → Claude 规划 → 用户确认 → Claude 执行 → 验证结果
         ↑                                        ↓
         └────────── 迭代优化 ←───────────────────┘
```

**三种工作流模式**:

| 模式 | 特点 | 适用场景 |
|------|------|---------|
| **Interactive** | 每步确认 | 复杂任务、高风险操作 |
| **Auto** | 自动执行 | 简单任务、低风险操作 |
| **Hybrid** | 混合模式 | 中等复杂度任务 |

### 模式 1: 工具封装 (Tool Wrapper)

**核心价值**: 让 Agent 按需获取特定库的上下文

**适用场景**:
- 团队内部 API 规范
- 框架最佳实践
- 业务领域知识

**实现模板**:

```yaml
# skills/api-expert/SKILL.md
---
name: api-expert
description: "团队 API 规范。在构建、审查或调试 API 时使用。"
metadata:
  pattern: tool-wrapper
  domain: internal-api
---

你是团队 API 专家。按需加载以下规范：

## 核心规范
加载 'references/api-spec.md' 获取完整规范。

## 审查代码时
1. 加载规范
2. 对照检查
3. 给出修复建议

## 编写代码时
1. 加载规范
2. 严格遵循
3. 生成符合标准的代码
```

**目录结构**:
```
api-expert/
├── SKILL.md (核心指令 <100 行)
└── references/
    ├── api-spec.md (API 规范)
    └── gotchas.md (踩坑清单)
```

### 模式 2: 生成器 (Generator)

**核心价值**: 强制输出一致性

**适用场景**:
- 文档生成
- 报告生成
- 代码脚手架

**实现模板**:

```yaml
# skills/report-generator/SKILL.md
---
name: report-generator
description: "生成结构化技术报告。当用户要求撰写报告时使用。"
metadata:
  pattern: generator
  output-format: markdown
---

你是技术报告生成器。严格按步骤执行：

第一步：加载 'references/style-guide.md' 获取格式规则。

第二步：加载 'assets/report-template.md' 获取输出结构。

第三步：询问用户缺失信息：
- 主题
- 关键发现
- 目标受众

第四步：按模板填充内容。

第五步：返回完整的 Markdown 文档。
```

**关键机制**: "填空" 流程 → 确保输出结构固定

### 模式 3: 审查器 (Reviewer)

**核心价值**: 将"检查什么"与"如何检查"分离

**适用场景**:
- 代码审查
- 安全审计
- 质量检查

**实现模板**:

```yaml
# skills/code-reviewer/SKILL.md
---
name: code-reviewer
description: "审查 Python 代码质量。当用户提交代码请求审查时使用。"
metadata:
  pattern: reviewer
  severity-levels: error,warning,info
---

你是 Python 代码审查员。严格遵循流程：

第一步：加载 'references/review-checklist.md' 获取审查标准。

第二步：仔细阅读代码，理解其目的。

第三步：将每条规则应用于代码。对于每处违规：
- 记录行号
- 分类严重程度：error/warning/info
- 解释为什么是问题
- 给出修复建议

第四步：生成结构化报告：
- 摘要
- 发现（按严重程度分组）
- 评分（1-10）
- 三大建议
```

**关键机制**: 检查清单可替换（Python 风格 ↔ OWASP 安全）

---

### 模式 4: 反转 (Inversion)

**核心价值**: 防止 Agent 在需求不明确时乱猜

**适用场景**:
- 需求收集
- 项目规划
- 架构设计

**实现模板**:

```yaml
# skills/project-planner/SKILL.md
---
name: project-planner
description: "通过结构化提问收集需求。当用户说'我想构建'时使用。"
metadata:
  pattern: inversion
  interaction: multi-turn
---

你是需求访谈专家。在所有阶段完成前，不得开始构建。

## 第一阶段 - 问题发现（每次只问一个问题）
- Q1："这个项目解决什么问题？"
- Q2："主要用户是谁？"
- Q3："预期规模是多少？"

## 第二阶段 - 技术约束
- Q4："部署环境是什么？"
- Q5："技术栈要求？"
- Q6："不可妥协的要求？"

## 第三阶段 - 综合（仅在所有问题回答后）
1. 加载 'assets/plan-template.md'
2. 填充模板
3. 呈现计划
4. 迭代直到确认
```

**关键机制**: 门控指令（不得跳过阶段）

---

### 模式 5: 流水线 (Pipeline)

**核心价值**: 强制执行带检查点的严格工作流

**适用场景**:
- 文档生成流水线
- CI/CD 流程
- 多步骤任务

**实现模板**:

```yaml
# skills/doc-pipeline/SKILL.md
---
name: doc-pipeline
description: "从代码生成 API 文档。当用户要求生成文档时使用。"
metadata:
  pattern: pipeline
  steps: "4"
---

你是文档生成流水线。不得跳过步骤。

## 第一步 - 解析与清点
分析代码，提取所有公开 API。询问："这是完整的 API 吗？"

## 第二步 - 生成文档字符串
对于每个缺少文档的函数：
- 加载 'references/docstring-style.md'
- 生成文档字符串
- 逐一呈现供用户确认

在用户确认前，不得进入第三步。

## 第三步 - 组装文档
加载 'assets/api-doc-template.md'。编译成单一文档。

## 第四步 - 质量检查
对照 'references/quality-checklist.md' 审查：
- 每个公开符号已文档化
- 每个参数有类型和描述
- 每个函数有使用示例
```

**关键机制**: 菱形门控（用户确认才能进入下一阶段）

```python
# Claude Code 可以直接调用这个工具
```

### 2. Sub-Agents 协同

**核心概念**: 让多个专业 Agent 协作完成复杂任务

**架构** (来自 Claude Code 源码):
```
┌─────────────────────────────────────────────┐
│ 主 Agent (Coordinator)                      │
└──────┬──────────────────────────────────────┘
       │
       ├─────▶ Implementer Sub-Agent
       │       - 负责实现代码
       │       - 独立上下文
       │
       ├─────▶ Spec Reviewer Sub-Agent
       │       - 检查是否符合规格
       │       - 独立上下文
       │
       └─────▶ Code Quality Reviewer Sub-Agent
               - 检查代码质量
               - 独立上下文
```

**双阶段审查**:
```
第一阶段: Spec Compliance（是否做了要求的）
第二阶段: Code Quality（是否做得好）
```

**关键原则**: 每个 sub-agent 使用全新上下文，避免污染

### 4. HANDOFF.md（会话连续性）

### 问题

长会话压缩后，下一个 Claude 实例不知道之前做了什么，导致重复劳动或方向偏差。

### 解决方案

开新会话前，让 Claude 写一份 HANDOFF.md：

```markdown
# HANDOFF.md - 当前任务交接

## 当前进展
- ✅ 已完成：用户认证 API（JWT）
- 🔄 进行中：权限管理（RBAC）
- ❌ 阻塞：数据库迁移脚本

## 尝试过的方案
1. ✅ **JWT 认证**（已验证可行）
   - Token 过期时间 7 天
   - 使用 bcrypt 加密密码
   - 刷新 Token 机制完成

2. ❌ **Session 认证**（性能不达标）
   - Redis 连接池配置太小
   - 高并发下延迟 > 500ms
   - 改用 JWT 解决

3. 🔄 **RBAC 权限**（正在调试）
   - 权限表设计完成
   - 角色关联逻辑待实现
   - 需要测试性能

## 踩过的坑
- **密码加密**: 必须用 bcrypt（不是 SHA256），否则无法验证
- **Token 过期**: 7 天合适，24 小时太短导致频繁重新登录
- **Redis key**: 必须加前缀 `app:cache:`，否则和其他服务冲突
- **数据库迁移**: 不要用 `drop_all()`，会丢失生产数据

## 下一步
1. 完成 RBAC 权限 API（预计 2 小时）
2. 添加单元测试（覆盖率目标 80%）
3. 更新 API 文档（Postman collection）
4. 部署到测试环境验证

## 相关文件
- `src/auth/` - 认证模块
- `src/models/permission.py` - 权限模型
- `tests/test_auth.py` - 测试（当前覆盖率 65%）
- `docs/api.md` - API 文档
```

### 用法

```
步骤 1: 当前 Claude 写交接文档
"请写一份 HANDOFF.md 总结当前进展，包括完成的工作、尝试过的方案、踩过的坑、下一步"

步骤 2: 快速审查
扫一眼 HANDOFF.md，有缺漏直接让 Claude 补充

步骤 3: 开新会话
"读取 HANDOFF.md，继续之前的任务"
```

### 核心价值

> HANDOFF.md 让下一个 Claude 实例**只看这个文件**就能继续任务，**不依赖压缩算法的摘要质量**

### 5. AI 审 AI（Plan Mode 进阶）

### 核心玩法

一个 Claude 写计划，另一个 Claude 审计划，**AI 审 AI**：

```
┌─────────────────────────────────────┐
│ Claude 1: 写计划                     │
│                                     │
│ 任务: 分析需求                       │
│ ├─ 理解业务目标                     │
│ ├─ 识别技术约束                     │
│ └─ 设计实现方案                     │
│                                     │
│ 输出: 实现计划.md                    │
└──────────┬──────────────────────────┘
           │ 计划文档
           ▼
┌─────────────────────────────────────┐
│ Claude 2: 审查计划                   │
│                                     │
│ 任务: 找漏洞、评风险                 │
│ ├─ 检查逻辑漏洞                     │
│ ├─ 评估性能风险                     │
│ ├─ 验证技术可行性                   │
│ └─ 提出改进建议                     │
│                                     │
│ 输出: 审查报告.md                    │
└──────────┬──────────────────────────┘
           │ 反馈
           ▼
┌─────────────────────────────────────┐
│ Claude 1: 修改计划                   │
│                                     │
│ 任务: 根据反馈调整                   │
│ ├─ 回应审查意见                     │
│ ├─ 修正设计缺陷                     │
│ └─ 确认最终方案                     │
│                                     │
│ 输出: 最终计划.md                    │
└─────────────────────────────────────┘
```

### 启动方式

1. 按 **Shift+Tab** 进入 Plan Mode
2. Claude 1 写完计划后
3. 开新 Claude 实例（或 Codex）审查
4. 迭代优化直到满意

### 适用场景

- **复杂重构**: 跨多个模块，影响面大
- **架构迁移**: 从单体到微服务，从 SQL 到 NoSQL
- **关键功能**: 支付、认证、权限等高风险模块
- **上线评审**: 重要变更上线前

### 审查维度

| 维度 | 检查点 |
|------|--------|
| **逻辑完整性** | 是否考虑了所有边界情况？ |
| **性能影响** | 会不会引入性能瓶颈？ |
| **安全性** | 有没有安全漏洞？ |
| **可维护性** | 代码是否容易理解和修改？ |
| **测试覆盖** | 测试计划是否完整？ |
| **回滚方案** | 出问题如何快速回滚？ |

### 实战示例

```
用户: "重构用户认证模块"

Claude 1（写计划）:
## 重构计划
1. 引入 JWT 替换 Session
2. 添加刷新 Token 机制
3. 权限系统升级为 RBAC
...

Claude 2（审计划）:
## 审查报告
### 逻辑漏洞
- ❌ 没有考虑 Token 被盗用的情况

### 性能风险
- ⚠️ RBAC 权限检查每次查询数据库，建议加缓存

### 安全问题
- ❌ 刷新 Token 没有 IP 绑定，可能被滥用

### 建议
1. 添加 Token 黑名单机制
2. RBAC 权限缓存到 Redis
3. 刷新 Token 绑定 IP + User-Agent

Claude 1（改计划）:
## 最终计划
...（根据反馈调整）
```
