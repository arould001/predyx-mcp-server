# CLAUDE.md 工作流设计

> 来源：Claude Code 团队 Boris Cherny 透露的内部 AI 工作流
> 核心：让 AI 从"被动应答"进化成有记忆、会规划、能自我迭代的队友

---

## 一、Workflow Orchestration（工作流编排）

### 1. Plan Node Default（规划优先）
- 任何非简单任务（3+ 步骤或架构决策）先进入规划模式
- 如果出问题，**立即停止并重新规划** —— 不要硬推
- 用规划模式做验证步骤，不只是构建
- 提前写详细规格，减少歧义

### 2. Subagent Strategy（子代理策略）
- 大量使用子代理保持主上下文窗口清洁
- 把研究、探索、并行分析卸载给子代理
- 复杂问题 → 扔更多算力（通过子代理）
- 每个子代理专注一个任务

### 3. Self-Improvement Loop（自我优化循环）⭐
- **用户任何纠正后**：立即更新 `tasks/lessons.md`
- 为自己写规则，**防止同样的错误**
- 无情地迭代这些教训，直到错误率下降
- 会话开始时回顾相关项目的教训

### 4. Verification Before Done（完成前验证）
- 永远不要没有证明它工作就标记任务完成
- 相关时对比 main 和你的更改的差异
- 问自己："Staff Engineer 会批准这个吗？"
- 运行测试、检查日志、证明正确性

### 5. Demand Elegance（追求优雅）
- 非简单更改：暂停问"有没有更优雅的方式？"
- 如果修复感觉很 hacky："知道我现在知道的一切，实现优雅的解决方案"
- 简单明显的修复跳过 —— 不要过度工程
- 在呈现之前挑战自己的工作

### 6. Autonomous Bug Fixing（自主修复 Bug）
- 给 Bug 报告时：**直接修复**，不要请求手把手
- 指向日志、错误、失败的测试 —— 然后解决它们
- 用户零上下文切换
- 不需要被告知如何修复失败的 CI 测试

## 二、Task Management（任务管理）

1. **先规划**：写计划到 `tasks/todo.md`，带可勾选项
2. **验证计划**：开始实现前确认
3. **跟踪进度**：边做边标记完成
4. **解释更改**：每步给高层总结
5. **记录结果**：在 `tasks/todo.md` 添加审查部分
6. **捕获教训**：纠正后更新 `tasks/lessons.md`

---

## 三、Core Principles（核心原则）

- **简洁优先**：每个更改尽可能简单，影响最小代码
- **不偷懒**：找到根本原因，不做临时修复，高级开发者标准
- **最小影响**：更改只触及必要的东西，避免引入 bug

## 四、对我们记忆系统的启发

### 可以借鉴的机制

| CLAUDE.md | 我们的系统 | 差距 |
|-----------|-----------|------|
| lessons.md | TROUBLESHOOTING.md | ❌ 没有"规则生成" |
| 自我优化循环 | 知识复利 | ❌ 没有"防错规则" |
| 会话开始回顾 | Heartbeat 检查 | ✅ 类似 |

### 建议新增：rules.md

```markdown
# tasks/rules.md

> 自动生成的防错规则，每次会话自动加载

## 规则 #1：信息回复先查询
- **来源**：Perodua 电车事件
- **规则**：最新信息必须联网验证再回答
- **优先级**：P0

## 规则 #2：飞书消息正确方式
- **来源**：sessions_send 报错
- **规则**：永远用 message(channel=feishu, target=...)
- **优先级**：P1
```

### 触发机制

```
用户纠正 /end → 话题总结 → 判断是否需要新规则 → 写入 rules.md
```

## 五、总结

CLAUDE.md 的核心创新：

1. **不只是记忆** —— 是**学习**
2. **不只是存储** —— 是**生成规则**
3. **不只是回顾** —— 是**防错**

> "同样的需求，别人用 AI 改三遍，你一次过。这就是配置和不配置的差距。"
